---
title: External VCS provider protocol
description: Implement an out-of-tree version-control adapter for Herdr.
---

An external VCS provider is a short-lived executable that translates a native
version-control system into Herdr's normalized model. Herdr starts a new process
for each request, writes exactly one JSON object to standard input, closes input,
and reads exactly one JSON response from standard output. Standard error is for
bounded diagnostics only and is never parsed as data.

The provider must not assume that its VCS has Git-compatible commands, output, or
capabilities. It owns discovery-independent command execution and parsing. Herdr
owns marker discovery, timeouts, output limits, capability policy, and checkout
workspace orchestration.

## Envelope

Every request contains `protocol_version`, a numeric `request_id`, and an
`operation`. The response repeats the version and request ID:

```json
{
  "protocol_version": 1,
  "request_id": 42,
  "operation": "describe"
}
```

```json
{
  "protocol_version": 1,
  "request_id": 42,
  "status": "ok",
  "response": {
    "operation": "describe",
    "capabilities": ["inspect", "checkout.list"]
  }
}
```

Provider errors use a structured result. `code` is provider-defined and stable;
`message` is safe to show to a user:

```json
{
  "protocol_version": 1,
  "request_id": 42,
  "status": "error",
  "error": {
    "code": "checkout_in_use",
    "message": "the checkout is in use",
    "retryable": false
  }
}
```

A nonzero exit status, malformed/oversized JSON, mismatched request ID, or timeout
is an adapter failure rather than a semantic VCS response. Providers should ignore
unknown request fields. Herdr ignores unknown advertised capabilities and response
fields.

## Exact paths

Paths use a tagged representation so Unix non-UTF-8 names and Windows native paths
round-trip without loss:

```json
{ "encoding": "utf8", "value": "/absolute/repository" }
```

On Unix, non-UTF-8 paths use base64-encoded native bytes with encoding
`unix_bytes_base64`. On Windows, non-Unicode-safe transport uses base64-encoded
little-endian UTF-16 code units with encoding `windows_utf16_le_base64`. Paths in
provider responses must be absolute and must not contain NUL.

## Operations

### `describe`

The provider returns any supported subset of:

- `inspect`
- `checkout.list`
- `checkout.create`
- `checkout.remove`
- `checkout.remove.force`

Herdr intersects this list with its own supported set and the provider's configured
`allow` list. `checkout.remove` additionally requires `checkout.list`, which Herdr
uses to validate the managed checkout before stopping its workspace runtimes and
to reconcile timeouts. `describe` itself is always permitted.

### `inspect`

Herdr batches up to 256 repository roots:

```json
{
  "protocol_version": 1,
  "request_id": 43,
  "operation": "inspect",
  "roots": [{ "encoding": "utf8", "value": "/repo" }]
}
```

The successful response has `operation: "inspect"` and an `items` array. Each item
contains the exact `root`, optional `branch`, and optional nonnegative `ahead` and
`behind` counts. Omit facts the VCS cannot provide; do not invent Git equivalents.

### `checkout.list`

The request contains one `root`. The response contains `checkouts`, each with a
provider-stable opaque `id`, display `name`, absolute `path`, and `managed` boolean.
Only managed checkouts are eligible for provider-backed removal.

### `checkout.create`

The request contains `root`, a user-entered `name`, and an absolute `destination`.
The response contains the created checkout in the same shape as `checkout.list`.
The provider decides how `name` maps to its native branch or checkout model.
The returned path must identify the requested destination. Herdr canonicalizes
paths for conflict detection; a successful response that points at a different
checkout is treated as an unknown outcome and quarantined for manual
reconciliation.

### `checkout.remove`

The request contains `root`, the absolute checkout path, and `force`. A successful
response has `operation: "checkout.remove"` and no additional fields. Herdr only
sends `force: true` when both `checkout.remove` and `checkout.remove.force` were
allowed and negotiated. The provider, not Herdr, performs removal; Herdr never
falls back to recursively deleting an external checkout directory.

Opening an existing checkout is a Herdr workspace operation and therefore has no
provider protocol request.

## Mutation and timeout semantics

Herdr reserves a canonical checkout path while `checkout.create` or
`checkout.remove` is running. The same reservation registry is used by built-in
Git worktree operations, so overlapping Git and external-provider mutations are
rejected with `checkout_operation_in_progress`.

After an operation timeout, Herdr calls `checkout.list` to reconcile the result.
Creation is successful only when the requested destination is listed; removal is
successful only when the checkout is absent. Any other result is reported as
`checkout_outcome_unknown`, and the reservation remains quarantined for the rest
of the server process because retrying a mutation could duplicate or destroy
provider state.

Configuration reloads invalidate cached external VCS projections immediately.
Read-only list/open results started under the old configuration are rejected with
`vcs_configuration_changed`. A definitively successful create/remove result is
grandfathered and finalized even if the provider was changed or removed while it
was running; definite failures release the reservation normally.
